## Auth layers

Four independent authentication mechanisms exist across the stack, each covering a different set of routes. None of them fully overlaps with another — understanding which layer guards which path matters for reasoning about what's actually protected.

| Layer | Enforced by | Protects | Exempt / not covered |
| --- | --- | --- | --- |
| Caddy HTTP Basic Auth | `docker/caddy/Caddyfile` `basic_auth` blocks, single `admin` user, bcrypt hash in `compose.yml`'s `CADDY_ADMIN_HASH` | `/` and `/docs` and `/api/*` (portal catch-all), `/grafana` \+ `/grafana/*`, `/metrics` | `/ws`, `/media/*`, `/ari/*` — see below |
| ARI Basic Auth | `docker/etc-asterisk/ari.conf`, one user `aistack` | `/ari/*` (REST \+ the `/ari/events` WebSocket) | Nothing within `/ari/*` — this is ARI's only gate |
| SIP auth | `docker/etc-asterisk/pjsip.conf`, per-endpoint `type=auth` (e.g. `6001`) | REGISTER/INVITE on `transport-udp` and `transport-ws` (`/ws`) | `chan_websocket`'s `/media/*` has no independent auth of its own — see note below |
| Grafana login | Grafana's own auth, `GF_SECURITY_ADMIN_PASSWORD` | `/grafana/login` and anything requiring edit/admin rights | Viewing dashboards — `GF_AUTH_ANONYMOUS_ENABLED=true` (Viewer role) means Caddy's basic auth alone is sufficient to _view_ |

<Note>
  `prometheus`, `loki`, and `promtail` have **no route through Caddy at all** and no `ports:` entry in `compose.yml` — they're unreachable from outside the `aistack` Docker network by construction, so none of the four auth layers above applies to them (there's no exposed surface to protect). Log/metric data only ever leaves that internal network via Grafana, which is itself gated by Caddy's basic auth.
</Note>

### Why `/ws`, `/media/*`, and `/ari/*` are exempt from Caddy's basic auth

This is a deliberate design decision, documented directly in the Caddyfile and in `portal/app/docs/page.tsx`'s security checklist, not an oversight:

- **`/ws` and `/media/*`** are consumed by SIP/WebRTC clients (softphones, browser JsSIP/SIP.js instances, `chan_websocket` media clients) that have no mechanism to attach an HTTP `Authorization` header during the WebSocket handshake in the general case. SIP's own auth (SIP digest, per-endpoint in `pjsip.conf`) is what actually gates `/ws`. `chan_websocket`'s `/media/<connection_id>` path relies on the connection id itself being effectively an unguessable, per-call token generated by Asterisk (`MEDIA_WEBSOCKET_CONNECTION_ID`) — there's no separate credential check on that path.
- **`/ari/*`** already enforces its own HTTP Basic Auth (the `aistack` user in `ari.conf`) — a second layer at Caddy would be redundant friction, not additional security, since the credential would just be checked twice.

### Grafana anonymous Viewer, explained

```yaml
GF_AUTH_ANONYMOUS_ENABLED=true
GF_AUTH_ANONYMOUS_ORG_ROLE=Viewer
```

Grafana's _own_ login is not required to view dashboards, because Caddy's `basic_auth` already gates the entire `/grafana/*` path before a request reaches Grafana at all — requiring a second, separate Grafana login on top of that would just be redundant friction for viewers. Anonymous access here is scoped to **Viewer only**; editing or admin actions still require signing in at `/grafana/login` with the real Grafana admin credentials.

## Default credentials that exist today

<Warning>
  The PJSIP and ARI passwords have been rotated out of git entirely (see below); Grafana's admin password is still a committed plaintext default. Rotate it too before granting anyone edit/admin access beyond a trusted network.
</Warning>

| Credential | Where it's set | Default value | Notes |
| --- | --- | --- | --- |
| PJSIP endpoint `6001` password | `docker/etc-asterisk/secrets/pjsip_auth.conf` (gitignored, `#include`'d from `pjsip.conf`) | Rotated, not in git | Template: `secrets/pjsip_auth.conf.example`. Rotate by editing the secret file, then `docker compose exec asterisk asterisk -rx "module reload res_pjsip.so"` |
| ARI user `aistack` password | `docker/etc-asterisk/secrets/ari_secret.conf` (gitignored, `#include`'d from `ari.conf`) | Rotated, not in git | Template: `secrets/ari_secret.conf.example`. Must be kept in sync with `.env.aistack`'s `ARI_PASSWORD` (portal reads it at runtime — see [Runbook: rotating ARI credentials](/operations/runbook#rotating-ari-credentials)) |
| Grafana admin password | `compose.yml`, `grafana.environment.GF_SECURITY_ADMIN_PASSWORD` | `changeme` | Only gates `/grafana/login` (editing); viewing is already behind Caddy's basic auth. Not yet rotated. |
| Caddy `admin` basic-auth password | `compose.yml`, `caddy.environment.CADDY_ADMIN_HASH` (bcrypt hash) | Generated with `openssl rand -base64 18`, then hashed | The **plaintext password is stored outside the repo** — only the bcrypt hash is committed. See [Runbook: rotating the Caddy basic-auth password](/operations/runbook#rotating-the-caddy-basic-auth-password) for regenerating it. |
| Cloudflare Tunnel token (`cloudflared`) | `.env.aistack` (gitignored), `TUNNEL_TOKEN`, `env_file:` on `compose.yml`'s `cloudflared` service | Not in git | Template: `.env.aistack.example`. Must be named exactly `TUNNEL_TOKEN` — that's the env var `cloudflared` itself reads. |

### No-secrets-in-git pattern

Asterisk config files support `#include "path"` (resolved relative to the config directory, `/etc/asterisk` in this image — see `main/config.c`). Both `pjsip.conf` and `ari.conf` now `#include` a file under `docker/etc-asterisk/secrets/`, which holds the real `type=auth`/user credential block. That directory has its own `.gitignore` (`*`, `!.gitignore`, `!*.example`), so only the `.example` templates are tracked. Because `docker/etc-asterisk` is bind-mounted as a *directory* (not a single file — see `compose.yml`'s `asterisk.volumes`), new files placed under it (like `secrets/*.conf`) are visible inside the container immediately, no restart needed to see them; a config *reload* is still required for Asterisk to re-read `pjsip.conf`/`ari.conf` and pick up the changed `#include`.

The portal-side `ARI_PASSWORD` and the `cloudflared` `TUNNEL_TOKEN` follow the same pattern one level up: both are read from `.env.aistack` (repo root, gitignored, added to `.gitignore`'s `# aistack` section) via `env_file:` on their respective services in `compose.yml` — never inlined under `environment:`. `ARI_PASSWORD` is read server-side at runtime by `portal/lib/ari.ts` (not a `NEXT_PUBLIC_*` build-time var), so rotating it only needs `docker compose up -d portal`, no image rebuild. `env_file:` values are baked in at *container creation*, though — a plain `restart` does not pick up a changed `.env.aistack`; use `docker compose up -d <service>` (or `--force-recreate` if compose doesn't detect the change) after editing it.

Nothing above is a secret an attacker could recover from the repo itself anymore — the PJSIP and ARI values live only in gitignored files. Grafana's admin password is the one remaining plaintext default in `compose.yml`.

## Restricting network exposure: loopback + Tailscale-only binding

Caddy's `ports:` in `compose.yml` used to be `["7231:80"]`, which binds to all host interfaces (`0.0.0.0`). Because Docker's published-port DNAT happens ahead of the host firewall's `INPUT` chain, a host-level firewall like `ufw` with `default deny incoming` does **not** filter this — see [Lessons Learned: ufw does not filter Docker-published ports](/operations/lessons-learned#ufw-does-not-filter-docker-published-ports) for the full mechanism.

The mitigation that works _with_ Docker's networking instead of fighting it is to bind the published port to specific host IPs:

```yaml
# compose.yml, caddy service
ports:
  - "127.0.0.1:7231:80"        # loopback
  - "100.69.165.55:7231:80"    # Tailscale IP
```

With this, `7231` is only reachable from the host itself and through the Tailscale interface (`100.69.165.55`) — not from the host's public/LAN interface, regardless of `ufw` state. This is also called out in `portal/app/docs/page.tsx`'s security checklist.

## Public exposure via Cloudflare Tunnel (`sip.w3.run`)

The published port above is intentionally *not* how the public hostname `sip.w3.run` gets exposed — it's for tailscale/local access only. Public exposure instead goes through a `cloudflared` service added to `compose.yml`:

```yaml
cloudflared:
  image: cloudflare/cloudflared:latest
  command: tunnel --no-autoupdate run
  networks: [aistack]
  env_file: .env.aistack   # TUNNEL_TOKEN
  depends_on: [caddy]
  restart: unless-stopped
```

`cloudflared` makes an *outbound* connection to Cloudflare's edge — no inbound port is published for it. `TUNNEL_TOKEN` comes from `.env.aistack` (gitignored; see `.env.aistack.example`) via `env_file:`; it must be named exactly `TUNNEL_TOKEN` — that's the env var `cloudflared` itself reads (`cloudflared tunnel run --help`: `--token value ... [$TUNNEL_TOKEN]`), not e.g. `CF_TUNNEL_TOKEN`.

**Routing note — this is the part most likely to be configured wrong:** the tunnel's public hostname ingress, set in the Cloudflare Zero Trust dashboard (Networks → Tunnels → the tunnel → Public Hostname), must point `sip.w3.run` at **`http://caddy:80`** — the Caddy container's *internal* aistack-network address — **not** `localhost:7231` or the tailscale IP. `cloudflared` reaches Caddy over the same Docker network everything else uses; it never goes through the published port at all. Cloudflare preserves the original `Host` header end-to-end, which is what lets `docker/caddy/Caddyfile`'s host-scoped block (below) select the right routes.

Until a real token is set, `cloudflared` crash-loops (`restart: unless-stopped` keeps retrying) — this is expected and does not affect any other service. Set `TUNNEL_TOKEN` in `.env.aistack`, then `docker compose up -d cloudflared`.

### Host-scoped Caddyfile routes for `sip.w3.run`

`docker/caddy/Caddyfile` now has two site blocks. Caddy matches site addresses by specificity, so a request with `Host: sip.w3.run` is always served by the exact-host block below, regardless of write order — it never falls through to the catch-all:

```caddyfile
http://sip.w3.run {
    handle /ari* { reverse_proxy asterisk:8088 }
    handle /ws   { reverse_proxy asterisk:8088 }
    handle /media/* { reverse_proxy asterisk:8088 }
    handle { respond 404 }   # everything else -- no portal, no grafana, no /metrics
}

:80 {
    # unchanged catch-all: portal, /grafana/*, /metrics (basic auth) +
    # the same open /ari*, /ws, /media/* -- reachable via localhost /
    # the tailscale IP, or any Host header other than sip.w3.run
}
```

`sip.w3.run` only ever reaches the SIP/WebRTC/ARI surface, with no `basic_auth` (unchanged from before — SIP/WebRTC clients can't attach an `Authorization` header, and ARI enforces its own). Everything else — the portal, `/docs`, `/grafana/*`, `/metrics` — 404s under that hostname instead of falling through to a `basic_auth` prompt, so there's no signal to a public scanner that those routes even exist. All other `Host` headers keep the pre-tunnel behavior unchanged.

## TLS / wss roadmap

Everything in this stack runs over plain `http://`/`ws://` today:

- `docker/etc-asterisk/http.conf` has `tlsenable`/`tlsbindaddr`/`tlscertfile`/`tlsprivatekey` present but **commented out**.
- The portal's docs page examples use `ws://100.69.165.55:7231/ws`, matching this default.
- Caddy itself is capable of automatic TLS certificate provisioning for a real domain name (its most common use case), but the current Caddyfile only defines a `:80` site block — no TLS is configured at the edge either.

Two independent places TLS could be added, not mutually exclusive:

1. **Terminate at Caddy** — give it a real domain (Tailscale's MagicDNS name or a public domain) and Caddy will provision and renew certificates automatically; internal traffic from Caddy to the other containers can stay plain HTTP over the `aistack` network. This is the lower-effort option and the one the portal's docs page suggests first.
2. **Enable Asterisk's own TLS listener** — uncomment `http.conf`'s TLS block and mount real cert/key files, enabling `https://`/`wss://` directly against Asterisk's HTTP server (bypassing Caddy, or in addition to it for direct port-8088 access if that port is ever published).

Once either is in place, switch client examples in [Websocket reference](/reference/websocket) from `ws://` to `wss://`.

## The portal has no login of its own

The portal is read-only today (no mutating actions exposed through its `/api/*` routes), but it has no independent authentication layer — Caddy's basic auth is the only thing standing in front of it. The same is true of Grafana's viewer access. Treat both as trusted-network tools, or add a dedicated auth proxy in front, before exposing either further.

## Locking down `/metrics`

`docker/etc-asterisk/prometheus.conf` ships with `auth_username`/`auth_password` commented out. Caddy's `/metrics` route is behind basic auth, but if `8088` is ever published directly (the commented `ports:` block in `compose.yml`'s `asterisk` service), `/metrics` becomes reachable with no auth at all, bypassing Caddy entirely. See [Observability](/reference/observability#res-prometheus) for the fix.
